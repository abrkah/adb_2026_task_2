# Homework 3: Homework 2 revisited (throughput)

`src/Benchmark.java` runs a realistic transaction mix on the unchanged `blocking_data` table (50,000 tuples).
For each transaction a value p in [0,1) is drawn i.i.d.:

| p | Transaction |
|---|---|
| < 0.6 | READ: 3 random distinct tuples, one `SELECT data_value FROM blocking_data WHERE data_id = ?` each, prints the sum |
| 0.6 to 0.7 | INSERT: one new tuple (ids from 50,000 up; removed when the benchmark starts again) |
| 0.7 to 0.8 | SCAN: `SELECT sum(data_value) FROM blocking_data`, prints the result |
| >= 0.8 | WRITE: 3 single-tuple `UPDATE ... WHERE data_id = ?`, in generated (unsorted) order |

Ordered locking from Homework 2 is **removed** (writes are never reordered). Kept: restart of deadlock victims
(`40P01`) and escalation after 5 aborts (exclusive advisory gate lock), so every transaction commits.

## Running
```
javac -d out src/*.java
java -cp out:lib/postgresql-42.2.18.jar Benchmark threads=24 duration=30                    # continuous stream
java -cp out:lib/postgresql-42.2.18.jar Benchmark threads=1 count=50000 gate=false          # serial, fixed stream
java -cp out:lib/postgresql-42.2.18.jar Benchmark preset=optimized shareScans=true threads=24 duration=30
scripts/demo.sh [best|optimized|baseline] [threads]    # 30 s live demo
scripts/ablation.sh; scripts/sweep.sh; scripts/serial_vs_concurrent.sh; python3 scripts/summarize.py
```
Options (`key=value`): `threads`, `duration` (s, continuous stream) or `count` (fixed stream), `warmup`, `seed`,
`preset=baseline|optimized`, `out=sync|buffered|none`, `stmtCache`, `batchWrites`, `autocommitSingle`, `pipeline`,
`syncCommit=on|off`, `fillfactor`, `avTune`, `gate`, `maxOptimistic`, `shareScans`, `scanLanes`, `print`, `csv`, `label`.
Result lines go to stdout, the per-second monitor and the summary to stderr.

**Continuous stream / equilibrium:** closed loop. Every worker starts a new transaction as soon as its previous one
committed, so the number of transactions in the system is constant (= threads) and arrivals = commits. The thread count
is chosen at the knee of the throughput curve (90% of peak; Little's law X = N/R): 8 threads for the baseline, 24 for the
best version. Note: the 10% inserts grow the table (50,000 to ~139,000 rows in 30 s at full speed), so scans get more
expensive and throughput drifts down during long runs. Every benchmark run therefore starts from a freshly loaded table.

## Bottlenecks found (details: `results/profile/`)
1. Full table scan: 94% of PostgreSQL execution time (`pg_stat_statements`), 10% of the transactions.
2. Round trips: a point SELECT needs 7.5 µs on the server but ~0.2 ms per round trip; the Java client is idle
   (Java Flight Recorder: 12 CPU samples in 15 s, threads wait in socket reads).

## Fixes
- **One round trip per transaction** (`pipeline=true`, part of `preset=optimized`): the statements of a transaction are
  sent as one multi-statement prepared statement in autocommit mode. pgjdbc sends one Sync, so PostgreSQL runs them as one
  implicit transaction (checked: same `now()`, a failing statement rolls back the earlier ones). Still one statement per
  tuple, same write order.
- **Shared scans** (`shareScans=true`, separate variant): concurrently waiting SCAN transactions are answered by one
  execution of the query, whose snapshot is taken after all of them started (see `ScanSharer` in `Benchmark.java`).

## Results (MacBook, 10 cores, PostgreSQL 14, client and server on one machine; `results/summary.txt`)
| Same stream of 50,000 transactions | Time | Speed-up vs. serial |
|---|---|---|
| Serial (1 thread), baseline | 27.1 s | 1.0x |
| Concurrent baseline (16-32 threads) | 5.4 s | 5.0x |
| One round trip per transaction (16 threads) | 3.5 s | 7.8x |
| + shared scans (32 threads) | 1.4 s | 18.9x |

0 deadlocks in all runs. Throughput vs. threads: baseline peaks at ~9,300 tx/s (10 threads), one round trip at ~11,500 tx/s,
with shared scans ~38,000 tx/s (48 threads). Textbook tuning (`synchronous_commit=off`, fillfactor 70, autovacuum tuning,
statement cache, buffered output) changes throughput by less than 3%.

# Homework 2

Concurrent `Blocker` transactions on PostgreSQL: deadlocks, client-side restart, and starvation avoidance.

## Files
| File | Purpose |
|---|---|
| `src/Blocking.java` | Original program: produces row-level deadlocks, aborted tasks are lost |
| `src/RestartBlocking.java` | Aborted transactions (SQLSTATE `40P01`) are rolled back and restarted until they commit |
| `src/NoLiveLocks.java` | Deadlock and starvation avoidance: ordered row locking + restart + escalation to exclusive execution |
| `src/ConnectionFactory.java` | Local connection settings (database `deadlock_demo`, user `ab`) - adjust to your setup |
| `demo-output/` | Console logs of the runs used in the slides; `screenshots/` has console images rendered from these logs |

## Setup
1. PostgreSQL (tested with 14), create role and database:
   `CREATE ROLE ab LOGIN PASSWORD 'ab'; CREATE DATABASE deadlock_demo OWNER ab;`
2. JDBC driver 42.2.18 into `lib/` (`lib/*.jar` is git-ignored):
   https://jdbc.postgresql.org/download.html
3. Compile and run:
   ```
   javac -d out src/*.java
   java -cp out:lib/postgresql.jar RestartBlocking [tasks] [queriesPerTask] [threads]
   java -cp out:lib/postgresql.jar NoLiveLocks     [tasks] [queriesPerTask] [threads]
   ```
   Defaults: 30 tasks, 3 queries per task, 4 threads. Isolation level is READ COMMITTED.

## NoLiveLocks concept
1. **Ordered locking** - `SELECT ... ORDER BY data_id FOR UPDATE` locks all rows a task needs in one global order, so lock cycles rarely form.
2. **Restart** - the remaining deadlocks (predicates are re-evaluated under READ COMMITTED) are rolled back and retried with randomized backoff.
3. **Escalation** - after 5 aborts (`-DmaxOptimistic=n`) a task takes a PostgreSQL advisory lock exclusively and runs alone; every other transaction holds it shared. Without concurrent transactions it cannot be a deadlock victim, so it is guaranteed to commit. PostgreSQL queues lock requests, so the waiting task is not overtaken forever. The gate lives in the database, so it also works across several JVMs (all clients must use it; `-DskipSetup=true` joins an existing table).

## Results (one laptop, PostgreSQL 14, single runs)
| Setup | Original | RestartBlocking | NoLiveLocks |
|---|---|---|---|
| 30 tasks, 3 queries, 4 threads | 9.1 s, 21 of 30 committed | 6.3 s, 30 of 30 | 4.8 s, 30 of 30 |
| 200 tasks, 3 queries, 16 threads | - | 318.6 s (1 run), 880 deadlocks, worst task 48 attempts | 26.3 s (mean of 18.4, 23.6, 36.9 s), 8 to 66 deadlocks, worst task 6 attempts |

### Parameter sweep (tasks / queries per task / threads; all runs committed every task)
| Setup | RestartBlocking | NoLiveLocks |
|---|---|---|
| 10 / 1 / 1 | 0.5 s | 0.6 s |
| 30 / 0 / 4 | 0.1 s | 0.1 s |
| 30 / 1 / 4 | 1.1 s | 1.8 s (1 deadlock) |
| 30 / 3 / 1 | 2.0 s | 2.4 s |
| 30 / 10 / 4 | 45.3 s | 9.6 s (5 deadlocks) |
| 50 / 3 / 8 | 27.8 s | 10.5 s (14 deadlocks) |

With little contention (one thread or one query) the extra locking `SELECT` makes `NoLiveLocks` slightly slower; with contention it wins clearly.

### Repeats (mean of 3 runs)
| Setup | RestartBlocking | NoLiveLocks |
|---|---|---|
| 30 / 3 / 4 | 8.4 s (7.7, 8.5, 9.0) | 6.7 s (4.5, 4.9, 10.7) |
| 50 / 3 / 8 | 27.4 s (22.2, 17.2, 42.8) | 8.5 s (13.6, 2.3, 9.8) |

Runtimes vary a lot between runs; the ranking at higher contention was stable.

### Escalation and multi-process tests
With `-DmaxOptimistic=1` (forces escalations) 100 tasks / 16 threads finished 100 of 100 with 4 escalations. Two JVMs on the same table (100 tasks, 8 threads each) both finished 100 of 100 (8 and 6 escalations, no errors).
